# 优化项 v1：业务 Agent 提示词与 Skill 体系体检

> 范围：xiic-book-studio 业务 agent / skill / tool 三层。
> 涉及代码：`src-tauri/prompts/v2/*.md`、`src-tauri/skills/`、`src-tauri/src/{agent_tools,agent_run_service,genre_agent,genre_skill,workflow,tool_runtime,prompt_templates}.rs`。
> 体检时间：2026-09-05；代码复核：2026-09-09。
> 本文档记录审查结论与实施状态；代码改动按文末清单落地，未处理项仍明确标注为暂缓。

> 结论说明：本次复核发现，原登记中既有真实的维护/测试缺口，也有将已有保护机制误判为缺陷的表述。下文将“现状事实”“风险判断”和“建议改动”分开记录。

## 0. 背景与现状

业务侧 agent / skill / tool 三层结构：

```
[项目题材]  ─►  题材 Agent（4 种）+ 共享协议（COMPOSED_AGENT_PROTOCOL，仅 5 个合成 Agent）
                          │
                          ▼
                Stage Agent（按 stage 路由，15 个 v2 prompt）
                          │
                          ▼
              Skill（白名单附加：4 genre + 1 craft）+ 工具集（23 个）
```

| 维度 | 当前 | 来源 |
|---|---|---|
| Stage Agent 数 | 15 | `src-tauri/prompts/v2/*.md` |
| 题材 Agent 数 | 4（通用连载 / 都市异能 / 悬疑 / 男频修仙） | `src-tauri/src/genre_agent.rs` |
| Skill 数 | 5（4 genre + 1 craft） | `src-tauri/skills/{genres,craft}/*.md` |
| Tool 数 | 23 | `src-tauri/src/agent_tools.rs` |
| 共享协议 | `COMPOSED_AGENT_PROTOCOL`（4 条，仅 5 个合成 Agent） | `src-tauri/src/genre_agent.rs` |
| Prompt 模板版本 | `v2` | `src-tauri/src/prompt_templates.rs:6` |
| 上下文上限 | 24_000 字符 | `src-tauri/src/tool_runtime.rs:20` |

## 1. 问题登记

### P1-01 副 Agent 提示词过薄，但运行时契约并非全部缺失（10/15 个为单句）

**现象**
15 个 v2 prompt 中，`adoption / story_index / chapter_memory / continuity_ledger / continuity_check / context_search_plan / context_search_rerank / continuity_review / chapter_split_plan / artifact_revision` 共 10 个只有单句身份声明；`xianxia_power_fantasy` 是 Skill，不是 Stage Agent prompt：

| Prompt | 当前内容（节选） | 字节 |
|---|---|---|
| `adoption.md` | 你是小说资料整理 Agent。只从已批准来源提取可验证事实，不续写、不推断、不补齐。 | 115 |
| `story_index.md` | 你是小说连续性资料索引 Agent。只从已批准正文提取可验证实体、事件和原子事实，不续写、不推断。 | 136 |
| `chapter_memory.md` | 你是长篇小说的事实交接记录员。宁可漏记，也不能推断、合并或补写正文没有明确证明的事实。 | 130 |
| `continuity_ledger.md` | 你是小说连续性状态记录员。只从已通过正文提取可直接引用的状态变化，绝不补写或推断。 | 124 |
| `continuity_check.md` | 你是严格的小说状态核对器。只识别直接的、可由原文引证的状态引用，不推断。 | 109 |
| `context_search_plan.md` | 你是小说历史上下文检索规划器。只规划需要核对的历史人物、物件、地点、事件、状态或承诺。 | 130 |
| `context_search_rerank.md` | 你是小说历史上下文的证据筛选器。不能搜索、编造事实或改写候选，只能选择相关原文证据。 | 127 |
| `continuity_review.md` | 你是经验非常老到的网络小说总编和长篇连续性编辑，只指出真正会伤害连载可用性的多章问题。 | 130 |
| `chapter_split_plan.md` | 你是网络小说连载策划编辑，擅长把超载章节拆成两个可执行、可衔接、可写作的章节任务。 | 124 |
| `artifact_revision.md` | 你是长篇小说编辑助手，只负责在用户指定范围内重写一小段文字。 | 约 80 |

**运行时契约情况**
- `story_index`、`chapter_memory`、`continuity_ledger`、`continuity_check`、`context_search_plan`、`context_search_rerank`、`continuity_review`、`chapter_split_plan`、`artifact_revision` 等 9 个 Agent 的具体输出格式、证据要求或失败兜底，主要写在 Rust 运行时 user prompt 和解析/校验代码中；不是完全没有协议。典型位置包括 `chapter_memory.rs:239`、`story_index.rs:275-310`、`continuity_ledger.rs:246/282`、`workflow.rs:1285/1493/1643-1646` 和 `context_search.rs:268-307/625-655`。
- `adoption` 是明显例外：审查基线中 `adoption.rs:57-87` 裸取 Agent 后直接调用普通 chat，`parse_extracted_candidates` 在 `adoption.rs:852` 解析 JSON，但 Agent prompt 本身没有声明 JSON 输出结构、字段要求或失败处理方式；本轮已改为 `{"items":[...]}` 契约并补充解析测试。
- 这些 Agent 仍缺少统一的可见协作说明，但不能把所有契约缺失都归因于单行模板。

**对比**
- `orchestrator.md` 12 行（含 JSON schema + 任务类型枚举 + 规则清单）
- `draft.md` 7 行（含写作风格 + 章节结构 + 越界红线）
- 副 agent 大致 1 行，**密度差 7-12×**

**判断**
单句 prompt 这一事实成立，但对其中 9 个 Agent 来说，具体契约已经存在于运行时 user prompt 和解析/校验代码中；不能据此断言它们都会发生格式漂移。明确的契约缺口主要是 `adoption`，其 prompt 与 JSON 解析器没有对齐。

### P1-02 15 个 Agent 中仅 5 个合成，10 个副 Agent 裸取

**现象**
`src-tauri/src/genre_agent.rs` 的 `compose_stage_agent` 把 4 条共享边界规则（事实优先级 / Canon 边界 / 未知处理 / 阶段职责）拼到 `system_prompt`。

需要纠正的是，当前并不是 15 个 Agent 都经过该合成路径。按 Agent 计，只有 5 个 Agent 会通过 `get_agent_for_project_stage` 获取合成结果：`story_architect / draft / review / revision / orchestrator`。其余 10 个副 Agent 直接调用 `get_agent()`，不会经过 `compose_stage_agent`，也不会自动获得 `COMPOSED_AGENT_PROTOCOL`：

- `chapter_memory`：`chapter_memory.rs:141`；
- `continuity_ledger`：`continuity_ledger.rs:141`；
- `continuity_check`：`continuity_ledger.rs:287`；
- `story_index`：`story_index.rs:145`；
- `adoption`：`adoption.rs:57`；
- `context_search_plan / context_search_rerank`：`context_search.rs:133/178/240`；
- `artifact_revision / continuity_review / chapter_split_plan`：`workflow.rs:1239/1396/1554`。

5 个合成 Agent 的主要入口包括 `workflow.rs:300/775` 和 `agent_run_service.rs:258/448/1005/1125`；其中部分调用是运行时准备或提案阶段的重复取数，不代表新增 Agent 类型。

**已有的局部补偿**
`build_prompt_for_agent`（`src-tauri/src/workflow.rs:1876`）在 draft / review / revision 阶段又**各自**写了"事实边界 / 连续性优先级 / 修订约束卡"段，所以功能上 cover 住。

**风险**
- 共享协议与阶段协议仍需靠测试守住；本轮已增加 5 个合成 Agent 的最终 system prompt 完整性断言；
- 10 个副 Agent 不自动继承 `COMPOSED_AGENT_PROTOCOL`，这是当前明确的路由差异；它们必须依赖各自的运行时 prompt、解析器和校验器，而不是静默假设共享协议存在；
- 合成路径与裸 `get_agent()` 路径并存，新增副 Agent 时容易遗漏共享协议；
- 10 个副 Agent 的测试目前锁定路由登记和契约来源清单；尚未把每个运行时 user prompt 的完整语义做成统一 schema，这属于有意保留的职责差异。

**判断**
原文“stage 直跑有缺口”的方向成立，但应明确为：15 个 Agent 中 5 个经过题材合成，10 个副 Agent 直接取裸 Agent；后者不会获得 `COMPOSED_AGENT_PROTOCOL`。共享协议与阶段 prompt 重复、缺少完整性测试的风险已分别通过路由登记测试和本轮提示词收口处理。

### P1-03 Orchestrator 为 read-only，能力说明仍可更明确

**现象**
`start_orchestrator_turn`（`src-tauri/src/agent_run_service.rs:433`）用 `complete_json_chat`（普通 chat，不是 tool 循环），orchestrator **不持有任何 read 类工具**。

`v2/orchestrator.md` 已声明“只能读取项目资料、绝不能创建更新删除”，并要求需要执行时委托专业子 Agent。运行时使用 `complete_json_chat`，不进入工具循环，也没有直接挂载 read 工具。

当前真正的边界是：Orchestrator 获得的上下文只有项目标题、类型、简介、章节提示和用户消息；同时可委托任务类型中没有 `story_index`、`context_search_plan` 等历史检索型子任务。因此它无法直接回答很多历史事实问题，只能在现有允许的任务类型中选择委托或回复。

**建议**
- 在 `orchestrator.md` 明确“可见上下文”和“不可直接访问的资料”；
- 评估是否增加历史资料查询类委托类型；
- 保留当前 JSON 输出协议，不把未实现的工具能力写进 prompt。

**判断**
read-only 事实成立；“prompt 未声明能力边界”表述过重，属于说明仍可完善，而非当前协议缺失。

### P1-04 Skill 与 prompt 存在少量重复约束（3 组）

**现象**
源码中能确认的重复主要有以下 3 组：

| 约束 | 出现位置 |
|---|---|
| 章节不强制危险 / 反转 | `workflow.rs` 的 Draft/Review/Revision 运行时任务契约 |
| 只输出正文不写创作说明 | `workflow.rs` 的 Draft/Revision/局部修订运行时任务契约 |
| 优先完成 1 个主要章节功能 | `workflow.rs` 的 Draft 运行时任务契约及章节任务卡 |

**风险**
- 维护成本高（同一约束分散在 prompt、Skill 和运行时字符串中）；
- 约束漂移（多源难对齐）；
- 上下文预算可能被重复占用，但目前没有测量这些重复文本对最终 prompt 长度的独立影响。

**判断**
重复约束确实存在，但原文“4-6 处”和部分文件归属不准确。当前能确认的是 3 组、每组约 2-3 处；冗余是否改善模型稳定性仍需要实验验证。

### P1-05 `allowed_skill_keys` 概念混淆

**现象**
- `Agent.allowed_skill_keys`（`src-tauri/src/models.rs:129`）：单个 stage agent 的白名单，**用户可改**；
- `GenreAgentProfile.allowed_skill_keys`（`src-tauri/src/genre_agent.rs:65`）：题材 agent 的白名单，**写死为 primary + continuity_and_agency**；
- `WritingSkill.category`（`src-tauri/src/models.rs:748`）：DB 字段是字符串 `"genre"` / `"craft"`，**无 enum**。

**语义身份不一致**
`continuity_and_agency` 实际承担部分**协议级**约束：它被四个题材 profile 允许，但是否最终注入仍取决于 stage Agent 的 `allowed_skill_keys`。物理位置在 `src-tauri/skills/craft/continuity_and_agency.md`，分类仍是 craft，容易让“共享方法”和“可选 Craft Skill”的语义混在一起。

### P1-06 Story Architect 的资料卡约束在模板与运行时重复（已收口）

**现象**
审查基线曾在 `v2/story_architect.md` 默认 prompt 和运行时追加段中同时放置资料卡写入规则。当前 `story_architect.md` 只保留身份和高层 Canon 原则；`start_story_architect_run_internal`（`src-tauri/src/agent_run_service.rs:241`）仍由 `direct_story_architect_prompt` 生成任务 prompt，并调用 `tool_runtime::prepare_tools`。

需要纠正的是，`direct_story_architect_prompt` 在 `src-tauri/src/agent_run_service.rs:387-396` 明确调用了 `workflow::build_prompt_for_agent`，因此并非完全绕过通用 prompt 构建。

运行时继续追加完整的“结构化资料卡工作方式”，包括阶段类别白名单、已有卡片更新优先级和停止条件。

**本轮处理**
- 静态模板只负责身份和高层 Canon 原则；
- 运行时追加段作为资料卡工具调用的唯一执行契约，避免模板与代码各维护一份细则。

**判断**
原先的双轨重复成立，但已通过 canonical source 收口；Story Architect 仍然经过 `build_prompt_for_agent`，并在其后追加资料卡执行契约。

### P1-09 测试覆盖不均

**现象**
`src-tauri/src/prompt_templates.rs:43-69` 的 `every_builtin_agent_has_a_versioned_prompt` 只验证：

### P1-11 缺少结构化的题材合成元数据

**现象**
`compose_stage_agent` 用 `format!` 拼装，最终 `system_prompt` 的确会以 `# 共享 Agent 协议` 等标题开头，因此并非完全没有可识别标记。

当前缺少的是结构化元数据：例如是否已合成、使用的题材 profile、原始 stage Agent 标识。运行日志和 UI 主要只能通过 prompt 文本或 Agent 角色间接判断。

`src-tauri/src/agent_run_service.rs:258` 拿到的 `agent` 已经是 compose 后的产物；当前没有单独保存 compose 前的 base Agent 快照，因此无法结构化回放合成前后的差异。

### P1-12 NEG 实验档案未形成统一的代码级禁用清单

**现象**
`docs/prompt-experiments/negative-prompt-patterns.md` 记录了 NEG-001（reaction_and_pacing）、NEG-002（故事架构长约束补丁）、NEG-003（六字段短生产卡）3 个负向实验。

- `writing_skills` 的历史 `urban_mystery` Skill 会在数据库迁移中被标记为 `legacy` 且禁用，但这不是覆盖所有 NEG 实验的通用机制；

### P1-13 v2 缺少 prompt 版本 changelog，暂不存在所述的 v1 prompt 兼容问题

**现象**
`DEFAULT_PROMPT_VERSION = "v2"`（`src-tauri/src/prompt_templates.rs:6`），当前仓库只有 `prompts/v2`，且 Agent 表没有 per-agent prompt version 字段。因此：
- 没有 v1 prompt 兼容层这一事实成立，但“DB 里残留 v1 标记”的前提目前不存在；
- 没有 v2 变更日志（哪些相对 v1 是新增 / 删除 / 修改）；

**风险**

- 当前缺少正式的 v2 设计说明和变更记录；
- `prompts.default_version` 在 `db.rs:748-749` 初始化后，仓库内没有读取点，当前只是写入数据库的死设置，不参与 prompt 选择或迁移。

**判断**
缺少 changelog 和正式设计文档成立；“当前存在 v1 DB 兼容故障”不成立；`prompts.default_version` 未被消费这一运行时问题成立。

## 2. 改善建议（按投入产出排序）

| 优先级 | 改动 | 影响 | 投入 |
|---|---|---|---|
| 🟥 P0 | 为 `adoption` prompt 补充 JSON 输出结构、字段要求和失败兜底，并与 `parse_extracted_candidates` 对齐 | 高（消除已确认的契约缺口） | 小 |
