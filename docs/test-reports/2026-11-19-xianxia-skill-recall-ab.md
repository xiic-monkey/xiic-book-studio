## 三、关键发现：题材 Skill 此前从未真正注入（缺陷 F10）

### 3.1 现象

首轮 A/B（2026-11-19 那批，run 162/163/165/167）跑完后核对上下文，发现**四次的 user prompt 里都没有任何 Skill 正文**：

- 全库 17 条 `prepared_contexts` 搜索题材 Skill 正文特征串，命中数 **0**；
- A 组与 B 组的 prompt 段结构**逐段完全相同**（12 段，标签、内容长度全部一致），差异只有 `system_prompt` 里那两行声明文字；
- 两组的题材 Skill 段、craft skill 段都不存在。

### 3.2 根因

`workflow.rs` 的 `enforce_workflow_prompt_budget` 裁剪顺序是「先剥 Skill 段阶段细则 → 再整段移除低优先级段 → 最后字符压缩」。其中「整段移除」这一档的过滤条件是：

```rust
"skill_priority_0" => *priority == 0 && text.contains("Skill")
```

题材 Skill 段与 craft skill 段的渲染标题都含 "Skill"（`# 题材 Skill` / `# 写作 Craft Skill`），而 `prompt_section_priority` 把含 "Skill" 的段一律判为 priority 0。于是当工具结果段超长时（本轮实测约 10.7k 字符），裁剪一路降级到这一档，**把两个 Skill 段整段删掉**——而 `system_prompt` 的声明仍按「已注入」表述。

F1 建立的「声明与注入同源」只覆盖了 `enabled` 语义，没有覆盖预算裁剪这一层：声明说注入、实际被裁掉，**声明与注入脱节**。

### 3.3 修复

- 字符压缩阶段**跳过 Skill 段**（Skill 段是声明的兑现物，被压缩就等于再次脱节）；
- 剥阶段细则与整段删除都退到兜底位置：B1/B2 移除非 Skill 低优先级段 → 字符压缩非 Skill 段 → C 级剥 Skill 阶段细则 → D 级整段删除 Skill；
- 顺带修掉一个潜在死循环：压缩循环原用 `target = (current-excess).max(minimum).min(current-1)`，当所有可压段都到达下限时每轮只减 1 个字符；现改为在候选阶段就跳过已达下限的段，`target = (current-excess).max(minimum)` 严格递减；
- 新增单测 `budget_keeps_skill_sections_whole_while_other_sections_shrink`、`budget_keeps_skill_always_when_everything_else_is_squeezed`，并抽出 `prompt_section_floor`；
- 全量 `cargo test --lib`：**234 passed / 0 failed / 3 ignored**。

修复后 dev_api 的运行日志不再出现 Skill 段被丢，只剩 `[prompt-budget] dropped sections: ["# 历史检索上下文"]`。

### 3.4 对历史结论的影响（重要）

**2026-07-19 的 NEG-001（「常驻注入的 Skill 会与事实边界争夺注意力，导致硬问题召回下降」）建立在这套裁剪行为之上**，那轮的 Skill 正文同样很可能没有真正进入上下文。该结论需要重新评估，本报告不据本轮数据为它背书，也不直接推翻它——它应视为**待复核**。

## 七、判定

按预注册协议第六节，并按 2026-11-21 补记之五写定的补跑口径（先写定后执行）：

1. **组内离散检查**：A 组极差 1 条、B 组极差 1 条，均未达到「≥4 条」的阈值 → 不触发 INCONCLUSIVE。
2. **口径一**（严格，可复现）：B 组均值 0.250 < A 组均值 0.333 → 落入 NEGATIVE。
3. **口径二**（人工语义）：B 组均值 0.500 ≥ A 组均值 0.333，进入 POSITIVE 检验：major 均值 1.25 < 3.00（不增）✓，GT 外问题均值 3.25 vs 2.33（+0.92）。

**两套口径给出相反方向**，差异量级 0.08 – 0.17 条。组内单次召回全部落在 0–1 条区间，组间差异完全在噪声内，且结论对判定口径敏感。

→ **判定：`INCONCLUSIVE`**（协议第六节第 5 条「未落入上述任一条 → INCONCLUSIVE，如实记录，不得强行归类」）。

按协议第六节补充约束，INCONCLUSIVE 必须回到 `docs/prompt-experiments/negative-prompt-patterns.md` 登记（已登记为 NEG-005）。

### 7.1 这个 INCONCLUSIVE 的真实原因

**不是「两组噪声大」，而是 ground truth 的覆盖面与模型可发现的问题集严重错配。**

7 次 run 里，模型稳定发现的是这些**成立但不在 GT 里**的问题：

| 问题 | 提出次数 | 是否成立 | 是否在 GT |
| --- | --- | --- | --- |
| 「内门清场队」是新行动方 | 5（A1/A2/A3/B1/B4） | 成立 | ✗ |
| 「赵吞赤髓」被刻在第三层铜门背面、断定是凶手署名 | 5 | 成立 | ✗ |
| 赵四平身份记录页 + 红笔「不承」批注 + 「第七次筛选」 | 4 | 成立 | ✗ |
| 黑牌金纹从低阶用途扩张为照出炉壁、与炉膛烬火同源 | 1 | 成立 | ✗ |
| 威胁断线（中段赵执事消失） | 5 | 成立 | ✗ |
| 零对白 / 对白质感 | 5 | 成立 | ✗ |
| 线索确认重复（「赵吞赤髓」第 4 次出现） | 4 | 成立 | ✗ |
| 收益未落地 | 2 | 成立 | ✗ |
| 开篇清点随身物件与第 4/5 章重复 | 1 | 成立 | ✗ |

而 GT 里的 9 条，有 7 条（GT-01~GT-06、GT-08）**几乎无人命中**——哪怕在基线 A 组。

原因很清楚：**GT-01~GT-06 全是「候选稿把第 3 章的动线与体感重构了」这一类细节冲突**（第三层空气冷/热、有没有石缝入口、假炉心室有没有门、尸体是否存在、在谷几年）。要发现它们，模型必须**回查第 3 章原文逐句比对**。而试读 Agent 拿到的是：

- 「最近已通过章节上下文」= **第 4 章结尾片段**（不是第 3 章）；
- 第 3 章全文只能靠 `search_story` 检索命中，而检索结果由模型自己决定查什么、且被预算裁剪优先丢弃（本轮 7 次都丢了「# 历史检索上下文」段）。

所以这些 GT 条目**在当前上下文供给下基本不可达**。这不是模型能力问题，是**事实边界检查受上下文供给限制**——比「题材 Skill 有害/无害」更值得记录。

## 八、偏差与限制（如实披露）

1. **F10 修复改变了被测系统**：本轮跑的是含 F10 的新二进制，2026-11-19 那批作废（Skill 正文未注入）。判定标准、指标、GT、候选稿均未改动。
2. **补跑轮次与口径是补记写定的**：B 组组内差异暴露后，追加 A3/B3/B4 并写定均值口径，写在协议补记之五、执行之前。
3. **样本量小**：A 组 3 次、B 组 4 次，召回基数 0–1 条 / 9 条，统计力接近零。任何 ±1 条的差异都不构成信号。
4. **模型侧不可控**：MiMO 单次调用存在偶发 `network error`，四臂统一最多重试 3 次，仅成功 run 计入。B1/B2 各发生过 1–2 次启动失败重试。
5. **执行环境**：2026-11-21 补跑首轮曾出现 `start_agent_run` 请求挂死（工具执行已完成但 `prepared_contexts` 未落库），重启 dev_api 后恢复正常，未产生脏数据。
6. **`continuity ledger unavailable`**：状态账本工具解析报 `missing field 'state_kind'`，7 次 run 均如此，走「继续试读」兜底分支。该问题存在于实验前，不构成组间差异。
7. **误报口径**：协议定义的「误报数」是「不在 GT 中、且经人工确认成立的问题数」。本报告 §七的「GT 外问题」列的是**数量**，人工复核确认其中绝大多数成立；但**未**把 GT 扩充为包含它们——GT 已定稿不得修改。
8. **与 2026-07-19 报告不可直接跨轮比较数值**：模型、temperature、thinking 设定与上下文供给均不同，本轮只比较 A/B 相对差。
9. **输出契约在报告定稿后变更（2026-11-21 晚）**：本报告的 7 次运行全部在旧契约下完成——提示词硬压「只输出 JSON 数组」，正文即产物。同日晚间，试读输出契约改为「结束时调用 `submit_review_issues` 工具提交」，产物变为 `{summary, issues}`。
   - **对结论的影响**：召回能力取决于模型能否发现 GT 内的问题，与结果用什么形状回传无关，因此本轮 INCONCLUSIVE 的判定与「GT 覆盖面错配」这一真实原因均不受影响。
   - **对可比性的影响**：严格说，被测系统已经变了。跨轮比较数值时必须声明契约版本；若要为新契约出一份可比的复测，需用同一 GT、同一候选稿（artifact 69）重跑，且新旧产物不可混算。
   - **未重跑**：截至本报告定稿，新契约只做过端到端跑通验收（run 175 / artifact 105、run 177 / artifact 106，两次均 `pending_human_approval`，工具调用 `submit_review_issues` status=success），样本量不足以支撑召回率统计。
