## 二、两个必须老板拍板的决策

这两条决定后面所有改动的语义，必须先定，否则改了还要返工。

### 决策 A：`review` 阶段算不算"可继续编辑"的阶段？

代码里现在两套口径：
- **口径 1（不含 review）**：`db.rs:3036/3076`、`v2_storage.rs:1197`、`workflow.rs:1073/1222`
- **口径 2（含 review）**：`workflow.rs:275/760/1257`、`agent_run_service.rs` 相关处

`review` 的实际语义是"试读报告"（`db.rs:4712` → `"试读报告"`，`prompt_templates.rs:32` → `review.md`），它产出的是**报告 JSON 而非正文**。按此语义，`review` 不该被当作可编辑正文阶段 —— 即口径 1 正确，口径 2 的 3 处是 bug。

**建议**：采用口径 1，把 `review` 从"可编辑正文阶段"中剔除，仅作为正文的评审输入。

### 决策 B：门禁是硬阻断还是软留痕？

- **硬阻断**：`approve_stage` 前必须先跑门禁，存在 `GateBlocker` 或质量分 < 72 时**拒绝**审批。风险：AI 评审不稳定时用户被卡死。
- **软留痕**：审批照常，但门禁结论（score / verdict / blockers）先算出来并**写进 `approvals` 表**，界面上显著提示"本次审批未通过门禁：xxx"。风险：用户可能依然无视。

**建议**：软留痕 + 显式二次确认。即：门禁不通过时审批仍可完成，但必须带上一条"已阅门禁风险"的确认记录，且该记录永久留在审批历史里。这样既保住核心卖点（决策有据可查），又不会把用户卡死。

## 三、修复批次

### 批次 0：给核心路径补测试网（前置，必须先做）

**为什么先做**：后面要动 `approve_stage` 与阶段流转，而这两处**当前零测试覆盖**。没有网就动核心状态机等于盲改。

**改动**
- 在 `db.rs` 的 `#[cfg(test)]` 中补 `approve_stage` 的用例，覆盖 4 条路径：正常审批 / 重复审批（验证幂等返回已有 approval）/ 跨项目审批（应拒绝）/ 阶段不匹配（应拒绝）。复用 `db.rs:5709` 已有的 `insert_artifact` 测试辅助。

**验收**：`cargo test` 全绿，新增用例 ≥ 6 条。
**风险**：无（纯新增）。

### 批次 1：`Stage` 类型收口（根因修复）

**目标**：让 14 处字符串判定收敛为 0，并让类型安全从"谎报"变成"真实"。

**改动**
1. `models.rs`：为 `Stage` 增加收窄通道
   ```rust
   impl Stage {
       pub fn from_db(raw: &str) -> AppResult<Stage> { /* 6 个分支，未知值返回 Validation 错误 */ }
   }
   ```
   同时补 `is_body_stage()`（返回 `matches!(self, Draft | Revision)`）与 `is_editable()`（按决策 A 定）。
2. 去掉类型谎报：把 2 处 `#[ts(type = "Stage")] pub stage: String` 改为真实的 `pub stage: Stage`（`models.rs:240` 的 `Artifact`、及另一处）。DB 读取处用 `Stage::from_db` 映射。**这一步是让 `contracts:check` 生成的 TS 类型与运行时一致的关键**。
3. 让 `Artifact.stage` 变 `Stage` 后，编译器会强制所有用到 `artifact.stage` 的地方改用 enum —— **让编译器列出完整的改动清单，数量由它决定，不靠人肉 grep**。
4. 收敛判定副本：`db.rs:3036/3076`、`v2_storage.rs:1197`、`workflow.rs:275/760/1073/1130/1222/1257/1334`、`agent_tools.rs:31` 全部改为调用 `Stage` 上的方法或复用 `CHAPTER_STAGES`。按决策 A 统一口径。

**验收**
- `grep -rn '"draft" | "revision"' src-tauri/src | wc -l` → **0**
- `grep -rn '#\[ts(type = "Stage")\]' src-tauri/src | wc -l` → **0**
- `cargo test` 全绿、`npm run contracts:check` 通过、`npx tsc --noEmit` 通过

**风险**：中等。`Artifact` 是跨前后端核心模型，类型变更会波及生成契约。务必在同一次提交内同步 `npm run contracts:generate`，否则前端类型与后端脱节。
**收益**：消灭整类"两套真相"bug，是批次 2 的前置。

### 批次 2：门禁语义落地 + 顺手把审批逻辑提出 `db.rs`

**技术障碍（必须先解决）**：`gate::analyze_chapter_gate` 是 **`async fn`**（内部调质量分析与 AI 评审），而 `db.rs:3025 approve_stage` 是**同步** `fn`，且内部用 `with_conn` 持有连接（闭包是 `FnOnce(&Connection)`，**无法在其中 await**）。直接把 gate 塞进 `approve_stage` 会撞上 sync/async 边界。

**解法：借这次机会把审批编排上移到 application 层** —— 一石二鸟，同时修掉评审清单里的"分层退化"。
- 在 `application/use_cases.rs` 新增 `approve_stage_with_gate`：先在 async 上下文里 `await` 门禁，拿到报告；再调用同步的 `db.rs approve_stage(.., gate_report)` 完成入库。
- `db.rs approve_stage` 增加 `gate_report: Option<&ChapterGateReport>` 参数，按决策 B 把 score / verdict / blockers 写入 `approvals`（需加列，走 `v2_storage` 已有的迁移框架，**不要再用 `CREATE TABLE IF NOT EXISTS` 硬扛**）。
- `commands.rs` 的审批命令改调新用例；`db.rs` 不再承载审批业务编排。

**验收**
- 集成测试：构造一份质量分 < 72 的产物 → 审批 → 断言 `approvals` 中记录了 gate 结论与 blocker 明细。
- `commands.rs` 中审批命令体量下降，业务逻辑不再出现在 `db.rs`。

**风险**：中高。涉及 schema 变更（`approvals` 加列）与命令链路改动。**建议在批次 1 完成后单独一个提交做**。

### 批次 3：嵌入模型缓存（独立、低风险、当天见效）

**现状**：`story_search.rs:493`（增量索引热路径）每章 `EmbeddingRuntime::load` —— 读 `pytorch_model.bin` + `tokenizer.json` 并对模型文件做 SHA256 校验；而 `:86`（全量重建）只 load 一次复用。**热路径反而比冷路径贵，N 章 = N 次全量加载 + N 次哈希。**

**改动**
- `AppState` 增加缓存字段（`OnceLock<Arc<EmbeddingRuntime>>`，或按模型版本号缓存以便换模型时失效）。**先确认 `EmbeddingRuntime` 是否 `Send + Sync`**，不满足则用 `Mutex<Arc<..>>` 包裹。
- `:493`、`:331` 改为从缓存取；`rebuild` 路径同样改为复用缓存。

**验收**：用 `src-tauri/src/bin/measure_local_embedding_rss.rs` 记录改动前后的 RSS 与加载次数；对 N 章语料实测增量索引耗时，改动后应随 N 近似线性（而非 N × 模型加载）。
**风险**：低。改动集中在一个模块，可独立提交、独立回滚。

## 五、明确不做（避免过度重构）

- **不重写 `db.rs`**。它 6474 行确实臃肿，但拆成多个文件不产生任何功能收益，且极易引入回归。批次 2 已把审批编排移出，剩余 CRUD 保持原样即可。
- **不动基础设施层**。连接池 PRAGMA（WAL / busy_timeout 5s / FK ON）、`with_conn` 同步闭包设计、AI 调用不在事务内、外键全显式 `ON DELETE`、密钥 AES-GCM 加密、全文无 XSS —— 这些都是做对的地方，改它们只有风险没有收益。
- **不引入新框架**。不引入 ORM、不引入状态管理库、不上编译期 SQL 校验（sqlx）。当前规模下收益不抵迁移成本。
- **不引入新的迁移框架**。`v2_storage.rs` 已有可用的 v8 迁移 runner，批次 2 直接复用它，不另造一套。

### 重要修正（推翻 09-10 评审中的三处误判）

1. **`approve_stage` 并非零覆盖** —— 实际有 15 处调用点，含幂等（`db.rs:6008`）与跨项目拒绝用例。09-10 直接采信了扫描结论未做验证。
2. **"含 review 的判定是 bug"是错的** —— `workflow.rs:275/760`、`agent_run_service.rs:995/1170` 里含 review 的判定，语义是"**可发起修订的源**"（修订可以基于试读报告），是正确的业务规则，不是规则漂移。并不存在两套真相，存在的是"规则没有名字，看起来像不一致"。
3. **`CHAPTER_STAGES` 等常量并非死代码** —— 有 20 处引用，一直在正常工作。

因此批次 1 的策略从"把所有集合统一成一个"改为"**给每个概念命名**"——不同业务场景本来就需要不同的阶段集合（正文 / 资料 / 章节级 / 可替换），强行合并会破坏业务规则。
